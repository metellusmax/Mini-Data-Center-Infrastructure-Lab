# Wireshark Network Traffic Analysis

## Overview

This phase of the Mini Data Center Infrastructure Lab focused on
observing and analyzing traffic generated by the segmented network.

Wireshark was installed on `admin-ws01` and used to capture traffic
between the ADMIN network, OPNsense, and `ubuntu-srv01`.

The objective was to connect packet-level behavior with concepts
configured earlier in the project, including:

- ARP
- Default gateways
- DNS
- Inter-subnet routing
- TCP connections
- SSH
- HTTP
- Firewall policy

---

## Environment

| System | Network | IP Address |
|---|---|---|
| `admin-ws01` | ADMIN | `192.168.1.111/24` |
| OPNsense ADMIN | ADMIN | `192.168.1.1/24` |
| OPNsense SERVER | SERVER | `10.10.20.1/24` |
| `ubuntu-srv01` | SERVER | `10.10.20.10/24` |

Because `admin-ws01` and `ubuntu-srv01` reside on different subnets,
traffic between the systems is routed through OPNsense.

## 1. ARP and Default Gateway Resolution

<img width="955" height="481" alt="Screenshot 2026-11-06 133939" src="https://github.com/user-attachments/assets/ef905862-90db-4645-8c1c-7651c7ac4371" />

Before sending traffic to `ubuntu-srv01`, `admin-ws01` used ARP to
identify the MAC address associated with its default gateway.

The capture showed:

```text
Who has 192.168.1.1? Tell 192.168.1.111
```

followed by the response identifying the MAC address associated with
`192.168.1.1`.

Because `10.10.20.10` is outside the local `192.168.1.0/24` subnet,
`admin-ws01` does not send Ethernet traffic directly to the Ubuntu
server's MAC address.

Instead, the workstation sends the local Ethernet frame toward its
default gateway, OPNsense.

**Key takeaway:** When communicating with a remote subnet, the IP
destination remains the remote system, but the local Layer 2 next hop
is the default gateway.

## 2. TCP Three-Way Handshake and SSH

<img width="933" height="188" alt="Screenshot 2026-11-06 135356" src="https://github.com/user-attachments/assets/c960df94-6c25-493e-8022-0aa4429fb981" />

An SSH connection from `admin-ws01` to `ubuntu-srv01` generated the TCP
three-way handshake:

```text
admin-ws01                         ubuntu-srv01

SYN                -------->
                   <--------       SYN-ACK
ACK                -------->
```

The connection used:

```text
Source:      192.168.1.111
Destination: 10.10.20.10
Port:        TCP/22
```

After the TCP connection was established, the SSH protocol exchange
began.

The capture also demonstrated the use of an ephemeral client port while
the Ubuntu server listened on the well-known SSH port TCP/22.

**Key takeaway:** TCP establishes the reliable transport connection
before SSH begins exchanging application data.

## 3. HTTP and Nginx

<img width="955" height="372" alt="Screenshot 2026-11-06 135802" src="https://github.com/user-attachments/assets/4dc8431f-f2db-4873-ad86-d0d0fc2ecd6f" />

An HTTP request was generated from `admin-ws01` to the Nginx service on
`ubuntu-srv01`.

The capture showed:

```text
SYN
SYN-ACK
ACK
GET / HTTP/1.1
HTTP/1.1 200 OK
FIN/ACK
```

The three-way handshake established the TCP connection to port 80.

The client then sent:

```text
GET / HTTP/1.1
```

and Nginx returned:

```text
HTTP/1.1 200 OK
```

This validated the complete path:

```text
admin-ws01
    |
TCP/80
    |
OPNsense
Routing + Firewall
    |
ubuntu-srv01
    |
Nginx
```

**Key takeaway:** TCP provides the connection while HTTP provides the
application request and response carried across that connection.

## 4. DNS Name Resolution

<img width="1278" height="452" alt="Screenshot 2026-11-06 140344" src="https://github.com/user-attachments/assets/f86939a1-8ac8-49db-8479-d6c39951b03e" />
<img width="661" height="622" alt="Screenshot 2026-11-06 140946" src="https://github.com/user-attachments/assets/89d98d52-e72a-4232-a9fc-9fc127cf029f" />

DNS traffic was captured while `admin-ws01` resolved `ubuntu.com`.

The workstation sent DNS queries to OPNsense:

```text
Source:      192.168.1.111
Destination: 192.168.1.1
Service:     DNS
Port:        53
```

The capture included an IPv4 A-record query for:

```text
ubuntu.com
```

and a response containing multiple IPv4 addresses.

AAAA queries were also observed for IPv6 resolution.

**Key takeaway:** DNS translates hostnames into IP addresses. DNS does
not carry the web content itself; it provides addressing information
that applications can use for subsequent network communication.

## 5. Firewall-Blocked TCP Connection

<img width="1272" height="105" alt="Screenshot 2026-11-06 143721" src="https://github.com/user-attachments/assets/3dcbde60-67c4-45a2-b50e-7a7c77e20bd0" />

The final test compared permitted traffic with traffic blocked by the
OPNsense firewall policy.

The ADMIN network was permitted to access `ubuntu-srv01` using:

```text
TCP/22 - SSH
TCP/80 - HTTP
```

TCP/443 was not permitted by the lab's ADMIN-to-SERVER policy.

A connection attempt to TCP/443 produced repeated SYN packets:

```text
SYN
SYN Retransmission
SYN Retransmission
SYN Retransmission
```

No SYN-ACK response was received.

This contrasted directly with the successful TCP/22 and TCP/80
connections, which completed the three-way handshake.

**Key takeaway:** Routing between two networks can function correctly
while firewall policy blocks a specific service or port.

## Protocol Summary

| Protocol | Observation | Concept Reinforced |
|---|---|---|
| ARP | Resolved the gateway's MAC address | Local Layer 2 delivery |
| DNS | Resolved a hostname to IP addresses | Name resolution |
| TCP/22 | Completed SYN, SYN-ACK, ACK | TCP connection establishment |
| SSH | Began after the TCP handshake | Application protocol |
| TCP/80 | Established HTTP connection | Port-based service connectivity |
| HTTP | GET request and 200 OK response | Web application traffic |
| TCP/443 | SYN retransmissions with no SYN-ACK | Firewall enforcement |

## Key Lessons Learned

This phase connected several networking concepts that had previously
been configured independently.

The traffic flow can be summarized as:

```text
ARP
Identify the local next hop
        |
        v
IP and Routing
Determine how to reach the destination network
        |
        v
Firewall Policy
Determine whether the traffic is permitted
        |
        v
TCP
Establish the connection
        |
        v
Application Protocol
SSH / HTTP / DNS
```

The most important lesson was that network connectivity should be
evaluated at multiple layers.

A functioning route does not guarantee that a particular TCP port is
permitted, and a reachable host does not guarantee that an application
service is available.

Wireshark provided packet-level visibility into the routing, service,
and firewall behavior configured throughout the earlier phases of the
lab.
